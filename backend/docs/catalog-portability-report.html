같은 버전·같은 파일은 중복 저장하지 않아요. 같은 버전의 다른 파일은 거부해요. 새 버전은 전체 저장 성공 후에만 활성화하고, 실패하면 전체 롤백해요. 이전 버전은 보존하며 이전 원본을 다시 지정해 되돌릴 수 있어요.

위치·상호는 네이버 API HUB 지역 검색, 메뉴 원자료는 네이버 지도 메뉴 페이지가 받은 구조화 데이터예요. 메뉴 수집 경로는 공식 지역 검색 API와 구분해요. DB 저장은 새로운 수집이나 판매 확인을 뜻하지 않아요.

현재 실행한 Compose 프로젝트는 opensourcesw예요. 아래 명령은 WSL 터미널에서 실행해요.

docker compose -p opensourcesw exec -T db psql -U suwon_app -d suwon_trip \

DB 볼륨을 삭제하지 않으면 앱·컨테이너가 종료돼도 자료가 남아요. 다른 PC에는 별도 볼륨이 만들어지므로 데이터 묶음으로 최초 적재해야 해요.

MVP 취향 속성 재정리

전체 속성 후보를 먼저 살펴보고 이번 시연에 필요한 최소 항목만 선택해요. 맛 3축 고정과 로컬 모델 실험은 철회했고 모델·생성 결과·전용 코드 브랜치·실험 테이블을 제거했어요. 기존 카페·메뉴와 V1 DB는 유지해요. 새 속성과 질문은 아직 확정하지 않았어요.

추천용 메뉴 기준

5,011건 중 40건은 시즌 종료, 4,971건은 판매 여부 미확인이에요. 판매 확정 메뉴는 현재 0건이에요. 메뉴 227건의 가격과 2,275건의 설명이 비어 있어요.

  1. 시연 자료, 판매 불가·시즌 종료 메뉴와 안내·선물·주류 같은 비추천 항목을 제외해요.
  2. 나머지는 검토 대상으로 두고, 음료·디저트·베이커리 분류와 근거를 기록해요. 분류가 불명확하면 추천하지 않아요.
  3. 가격·맛·식감·옵션 등 후보의 데이터 확보 여부를 확인하고 MVP에 넣을 항목만 선택해요. 미확인 값을 임의의 점수로 채우지 않아요.
  4. 판매 여부가 UNKNOWN인 메뉴를 시연 추천에 쓰면 화면에서 확인 필요 상태를 표시해요.

다른 사용자가 실행할 때

  1. DB 실행에는 #23 → #31, 파일 연결에는 #30의 코드가 필요해요. 인증 #19·설문 #26까지 합치는 전체 서비스 통합은 별도로 재검증해요.
  2. 버전 묶음을 원하는 경로에 풀고 압축 파일 해시, 파일별 해시와 manifest를 확인해요.
  3. Docker와 Compose를 준비해요. PR #30은 저장소 안의 고정 입력을 기본으로 읽으며, 다른 버전만 CATALOG_FILE로 지정해요. PR #30 실행 안내에 Windows·WSL·Linux·macOS 절차가 있어요.
  4. 확장 Compose로 실행해 세 서비스 health와 카탈로그 적재 로그·실제 DB 행 수를 확인해요. 파일 경로를 바꾸면 백엔드를 다시 생성해야 새 연결이 반영돼요.

이 보고서는 2026-11-18의 검증 스냅샷이에요. 실행 설정·안내 준비와 실제 환경의 동작 검증을 구분해 기록했어요. DB 적재·조회는 #24에서 검증했어요. 프론트 기능 API 프록시, 메뉴 HTTP API와 추천 점수 계산은 후속 작업이에요.
