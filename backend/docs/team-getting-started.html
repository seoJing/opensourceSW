처음 받는 팀원을 위한 작업 착수 안내

Git과 Docker를 준비하고, 저장소에 포함된 고정 카탈로그를 PostgreSQL에 적재해 같은 개발 출발점을 만듭니다.

현재 상태준비코드데이터실행DB 확인작업 시작

0. 먼저 확인할 것

이 안내서의 카탈로그 적재 절차는 PR #23 → #31 → #30이 main에 병합된 뒤 사용합니다.

작성 시점에는 세 PR이 미병합 상태입니다. 지금 main만 받으면 카페·메뉴 데이터 적재 기능은 없습니다. 병합 전에는 아래 1~2단계와 기본 환경 확인까지만 진행합니다. 여러 기능 브랜치를 직접 합치거나 코드를 복사할 필요는 없습니다.

구분필요한 PR가능한 일
공통 개발 환경현재 main프론트·백엔드·DB 실행 및 health 확인
실제 카탈로그 재현#23 + #31 + #30저장소의 JSON 검증 → PostgreSQL 적재 → SQL 조회
로그인·설문 연동#19 / #26 및 별도 실행 설정각 API 명세에 따라 설정 후 연동. 카탈로그 실행만으로 활성화되지 않음

이번 작업은 이미 수집한 고정 데이터를 재현하는 것입니다. 재수집·네이버 키 발급·브라우저 조작·LLM 설치는 필요하지 않습니다.

1. 처음 PC에서 준비

  1. Git을 설치하고, Docker Desktop을 설치·실행합니다. Linux는 Docker Engine과 Compose 플러그인으로 가능합니다.
  2. Windows는 Docker Desktop의 Linux containers 환경을 사용합니다. WSL에서 작업하면 해당 배포판의 Docker 통합을 활성화합니다.
  3. 아래 명령이 모두 성공하는지 확인합니다. Docker를 사용하는 실행 경로에는 Java·Maven·Node.js·PostgreSQL을 별도로 설치하지 않아도 됩니다.
git --version
docker compose version
docker info

아래 명령은 선택한 터미널 하나에서 계속 실행합니다. Windows PowerShell의 경로와 WSL/Linux 경로를 섞지 않습니다. 3000·8080 포트를 다른 앱이 사용하고 있다면 해당 앱부터 확인합니다.

2. 팀 저장소 받기

처음 받는 경우 작업할 부모 폴더에서 실행합니다. URL은 팀 원본 저장소입니다.

git clone https://github.com/seoJing/opensourceSW.git
cd opensourceSW
git status --short --branch

이미 저장소가 있는 경우 그 폴더에서 상태를 확인한 뒤, 변경 사항이 없는 경우에만 최신 main을 받습니다. 수정한 파일이 있다면 먼저 보존 방법을 담당자와 정합니다.

git status --short --branch
git switch main
git pull --ff-only origin main

이후 모든 Docker 명령은 docker-compose.yml이 있는 저장소 루트에서 실행합니다. 이 안내서는 실행 이름을 -p opensourcesw로 고정합니다. 기본 스크립트와 섞어서 여러 스택을 띄우지 않습니다. 같은 PC의 다른 체크아웃도 포트와 DB 볼륨을 공유하므로 한 세트만 실행합니다.

병합 전: 공통 환경만 확인하려면
docker compose -p opensourcesw -f docker-compose.yml config --quiet
docker compose -p opensourcesw -f docker-compose.yml up --build -d --wait
docker compose -p opensourcesw ps

http://localhost:3000/api/health의 status와 components.db.status가 모두 UP인지 확인합니다. 병합 전에는 여기까지입니다. 카탈로그 관련 PR이 병합되면 main을 다시 받은 뒤 아래 단계로 진행합니다.

3. 저장소 안의 실제 데이터 확인

PR #30에 아래 고정 데이터가 포함됩니다. 별도 압축파일 전달이나 압축 해제는 필요하지 않습니다.

backend/data/catalog/haenggung-2026-11-18.2/
├── catalog.json
├── manifest.json
└── SHA256SUMS
파일용도
catalog.json카페 320곳·메뉴 5,011건의 실제 입력. 출처 URL·외부 ID·관찰일 포함
manifest.json버전·수량·수집 범위·누락 정보·카탈로그 해시
SHA256SUMS두 JSON 파일의 바이트 동일성 검사

상호·주소·좌표 등은 네이버 API HUB 지역 검색 및 지도 목록 대조, 메뉴명·표시 가격·설명은 공개 지도 메뉴 페이지의 구조화 데이터에서 확인했습니다. 수집 관찰일은 2026-11-18입니다. 리뷰 본문·평점은 수집하지 않았고, 재료·취향 점수도 생성하지 않았습니다.

현재 판매를 확인한 데이터는 아닙니다. 메뉴 4,971건은 UNKNOWN, 40건은 SEASON_ENDED이며 가격 227건·설명 2,275건은 미확인입니다. 행궁동 전체 업소의 완전한 명부나 5,011건 모두의 추천 적합성을 의미하지 않습니다.

Windows PowerShell: 파일 및 해시 검사
$ErrorActionPreference = 'Stop'
$seed = 'backend/data/catalog/haenggung-2026-11-18.2'
foreach ($line in Get-Content -LiteralPath "$seed/SHA256SUMS") {
    $parts = $line -split '\s+', 2
    $actual = (Get-FileHash -LiteralPath (Join-Path $seed $parts[1]) -Algorithm SHA256).Hash
    if ($actual -ne $parts[0]) { throw "해시 불일치: $($parts[1])" }
    Write-Host "OK: $($parts[1])"
}
if (-not (Test-Path 'backend/compose.catalog.yml')) { throw 'PR #30 병합 여부를 확인하세요.' }
if (-not (Test-Path 'backend/src/main/resources/db/migration/V1__create_catalog.sql')) { throw 'PR #31 병합 여부를 확인하세요.' }
WSL / Linux / macOS: 파일 및 해시 검사
(
  set -eu
  cd backend/data/catalog/haenggung-2026-11-18.2
  if command -v sha256sum >/dev/null 2>&1; then
    sha256sum -c SHA256SUMS
  else
    shasum -a 256 -c SHA256SUMS
  fi
)
test -f backend/compose.catalog.yml
test -f backend/src/main/resources/db/migration/V1__create_catalog.sql

파일이 없거나 해시가 다르면 다음 단계로 진행하지 말고 병합 상태·다운로드 상태를 확인합니다. 원본 JSON을 편집하거나 IDE로 재저장하지 않습니다. 줄바꿈 변경도 같은 버전의 해시를 바꿉니다.

4. 카탈로그를 DB에 적재하며 실행

이 단계부터 #23·#31·#30 병합이 필요합니다. 기본 Compose와 카탈로그 확장을 함께 실행합니다. 저장소 안 JSON을 기본으로 읽으므로 개인 경로를 입력할 필요가 없습니다.

Windows PowerShell
Remove-Item Env:CATALOG_FILE -ErrorAction SilentlyContinue
docker compose -p opensourcesw -f docker-compose.yml -f backend/compose.catalog.yml config --quiet
if ($LASTEXITCODE -ne 0) { throw 'Compose 설정 검사 실패' }
docker compose -p opensourcesw -f docker-compose.yml -f backend/compose.catalog.yml up --build -d --wait
if ($LASTEXITCODE -ne 0) { throw '시작 실패. 아래 로그 확인 절차를 사용하세요.' }
WSL / Linux / macOS
unset CATALOG_FILE
docker compose -p opensourcesw -f docker-compose.yml -f backend/compose.catalog.yml config --quiet &&
  docker compose -p opensourcesw -f docker-compose.yml -f backend/compose.catalog.yml up --build -d --wait

기존 .env에 CATALOG_FILE을 지정했다면 해당 항목도 제거해야 기본 파일을 사용합니다. 다른 DB 계정·이름을 지정했다면 뒤의 SQL 명령도 맞춥니다. 처음에는 이미지와 라이브러리를 내려받고 테스트하므로 인터넷 연결이 필요하며 시간이 걸립니다.

docker compose -p opensourcesw ps
docker compose -p opensourcesw logs --tail=100 backend

세 서비스 db, backend, frontend가 모두 healthy여야 합니다. 최초 적재 로그는 Catalog stored in database: cafes=320, menus=5011, inserted=true입니다. 이미 같은 데이터를 넣었다면 inserted=false이며 중복 저장하지 않습니다.

5. 실제 PostgreSQL 데이터 확인

아래 명령은 PowerShell과 WSL/Linux에서 동일합니다. 로컬에 psql을 설치할 필요가 없습니다.

docker compose -p opensourcesw exec -T db psql -U suwon_app -d suwon_trip -c "SELECT data_version, cafe_count, menu_count, source_sha256 FROM catalog_dataset JOIN catalog_active USING (data_version);"
docker compose -p opensourcesw exec -T db psql -U suwon_app -d suwon_trip -c "SELECT COUNT(*) AS cafes FROM catalog_cafe JOIN catalog_active USING (data_version); SELECT COUNT(*) AS menus FROM catalog_menu JOIN catalog_active USING (data_version);"
docker compose -p opensourcesw exec -T db psql -U suwon_app -d suwon_trip -c "SELECT cafe_id, menu_id, name, price_krw, availability FROM catalog_menu JOIN catalog_active USING (data_version) ORDER BY ordinal LIMIT 10;"

활성 버전haenggung-2026-11-18.2
실제 카페 / 메뉴 행 수320 / 5011
원본 SHA-25677101fe31346de40225d23adca5a485f74cb4861e98a9a8e9d1cf7474ab4eb0d

브라우저에서 http://localhost:3000/와 http://localhost:3000/api/health도 확인합니다. health의 최상위 status와 components.db.status가 모두 UP이어야 합니다. 현재 화면은 상태 확인 화면입니다. 추천 화면·카탈로그 HTTP API·기능 API 프록시까지 완성됐다는 뜻은 아닙니다.

흐름: 저장소의 JSON → 입력 검증 → 트랜잭션 적재 → PostgreSQL → 서버의 DB 조회. JSON은 적재 원본이며 실행 중 데이터 저장소는 PostgreSQL입니다.

6. 종료와 다음 실행

docker compose -p opensourcesw -f docker-compose.yml down

일반 down은 컨테이너를 제거하고 DB named volume suwon_trip_postgres_data를 보존합니다. 데이터를 유지하려면 down -v를 사용하지 않습니다. JSON을 지우거나 볼륨을 직접 수정할 필요도 없습니다.

최초 적재 후에는 JSON을 연결하지 않고 기본 Compose만으로 다시 실행할 수 있습니다.

docker compose -p opensourcesw -f docker-compose.yml up --build -d --wait

카탈로그 확장을 계속 사용하는 것도 가능합니다. 동일 버전·해시는 중복 적재되지 않습니다. 다른 PC의 볼륨은 별개이므로 그 PC의 첫 실행은 4단계를 거칩니다.

7. 환경 확인 후 맡은 작업 시작

  1. AGENTS.md, CONTRIBUTING.md, docs/collaboration.md 및 담당 영역 README를 읽습니다.
  2. 본인 GitHub 계정으로 담당 Issue를 확인하고 수정 경로·완료 조건을 적습니다. 열린 PR과 수정 파일이 겹치면 병합 순서를 먼저 정합니다.
  3. 최신 main에서 본인 Issue 번호를 포함한 작업 브랜치를 만듭니다. 예: Issue 42라면 feature/backend/42-preference-definition. 실제 담당 번호와 작업명으로 정합니다.
  4. 변경한 영역의 검증을 마치고 작업 브랜치를 push한 뒤 main 대상 PR을 만듭니다. 원본 저장소 쓰기 권한이 없다면 본인 fork를 사용합니다. 다른 팀원의 계정을 공유하지 않습니다.
  5. 최소 1명 리뷰 후 저장소 규약에 따라 병합합니다. main에 직접 push하지 않습니다.
